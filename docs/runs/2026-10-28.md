## Issues / time sinks observed

1. Skill copies diverge (repo vs installed vs plugin). Agent must pick one; installed slab-run lacks the per-class spec detail that the repo slab-product-spec has.
2. Cowork's Linux sandbox has no `fitz` (PyMuPDF); `~/fusion-renders` (Windows home) is not visible to the sandbox, so run dir must be the Cowork outputs folder. Skills assume `uv run` on the Windows host.
3. Cloud already holds SLAB_TOP_v1..v3 + a stale "SLAB_TOP_v1 Drawing" — name derivation needed an extra query.
4. **GUI interaction during a run silently destroys work.** A stray click started a root `Sketch1` in edit mode between Class 2 and 3. Class 3 measured PASS in its own call, then the whole component vanished from the tree while later classes survived. Nothing errored. Mitigations: tell the presenter not to touch Fusion; at the start of each class assert `design.activeEditObject` is a Component (not a Sketch) and that all previously built occurrences still exist.
5. **Skill's timeline-health snippet is buggy.** `tl.item(i).entity.healthState` raises on occurrence entries (`'Occurrence' object has no attribute 'healthState'`). Use `tl.item(i).healthState` (TimelineObject) instead. Present in slab-run, fusion-scratch-build, fusion-mcp-driving.
6. **MCP `deltas` were right and I misread them (corrected after the run).** At Class 4 the deltas reported body_count 1 -> 2. I dismissed that as broken instrumentation, but Class 3 had already vanished, so only Upper + Panel existed. The bbox jump to X 148.9 / Z 125.8 was the stray sketch line. The deltas flagged the incident one call before I found it. Lesson for the skill: when deltas disagree with your own expected running total, stop and inspect the tree; don't explain it away.
7. **Spec label nit:** 'extrude 1522.926 cm³' in class 1 is the post-fillet volume; the raw extrude is 1524.9. Harmless, but it reads like a failed check.
8. **Fusion time is trivial.** Each class takes 0.1-0.5 s inside Fusion. Nearly all wall-clock time is agent turn latency (writing code, reading results), so token and turn count drive run time.
9. **Cold build took 6 min 12 s of wall clock** (start to 289 bodies saved), including the stray-sketch incident. Fusion compute was about 15 s of that. The skill's ~20 min budget is pessimistic for this agent; previous overruns came from repairs, stalls and context, not geometry.
10. **Legends passed first time** because the outline coordinates were computed analytically before drawing. Put the tested R/I/V outline coordinates in the spec (marked provisional, TBD-18) so every run gets this.
11. **Spec arithmetic uses padded bbox.** Measured tallest Z is 61.150; the spec's 61.18 includes the ±0.03 instrumentation pad, so DEC-C3 reads -15.15 measured vs -15.18 quoted. State both, or quote the measured value.
12. **The skill's `assign()` causes the CMF timeout.** `BRepFace.appearance` returns the *inherited* appearance (Steel - Satin on fresh bodies), so 'clear face overrides first' writes a face override on every face. Measured: 116 bodies took 40.9 s with 887 face writes; with body-first assignment, 173 bodies took 4.8 s with 0 face writes. Fix in slab-run §4 and fusion-mcp-driving §4: set `b.appearance` first, then fix only faces that still differ. The full pass drops to ~8 s and won't hit the 300 s timeout.
13. Spec says the end state has '11 appearances (ten SLAB_* + the library source)'. `addByCopy` from the library does not add the source; the 11th is the document default `Steel - Satin`. Wording nit.
14. Skill says a fresh document defaults to brightness 1.2. This one read **1000**. The 'write 1700 explicitly' rule still holds; the stated default is version- or document-dependent.
15. Cowork note: the `start_render` filename must be a Windows path the sandbox can also see (the outputs folder), or the host-side measurement scripts can't read the PNG.
16. **Biggest render time sink: the pad acceptance test can't pass with the spec'd CMF + brightness on this build.** Red clips at 255, so G:R stays above 0.59 and luminance above 166 at any emissive luminance from 25 to 150. Fixing it needs a calibration decision (pad albedo, or a brightness/exposure pair re-derived for both housing and pads). That's a spec owner's call, not something a run should loop on. Until it's decided, every run will either burn time tuning or report FAIL. Re-derive once, offline, and update the ladder table in fusion-photoreal-render.
17. **Pad measurement tooling.** measure_classes.py counts the power LED and highlights; color thresholds catch the orange knobs. Projecting pad centers with `viewport.modelToViewSpace` and sampling ROIs worked first time and is cheap. Make it the documented method and ship it as a utility (it measures; it doesn't build).
18. **Don't tune appearances in place during render calibration.** It can fork an undeletable duplicate. If tuning is ever needed, do it on a scratch copy before assignment, or decide the values offline.
19. Skill says `progress_percent` only reports 0/50/100; this build reports real values (24.2%).
20. composite.py output has an irregular light halo; investigate the keying tolerance before the next demo, because it's the image people see.
21. **Composite is broken on this build.** composite.py assumes a perfectly uniform backdrop and keys by flood-fill within ±6 of the modal colour. This render's plate varies 172-178 with noise, so the matte leaks: a halo on the hero, and the plan crop is pushed off the product. Looser tolerance doesn't fix it. Fix: make the difference matte (empty-plate render, same settings) the default path. It adds one render per view at final settings (~70-120 s); a cheaper empty plate might work if it matches. This is the image a demo audience sees first, so it's high priority.
22. **Worked-example sheet content leaks into every run.** slab_sheet.json has a fixed date and model name, padded extents shown as measured (61.21, 197.04), and a MATERIAL column (ABS+PC, Al 5052, TPE 60A, Silicone…) that the spec never states, since 'appearance is not a physical material'. Ship the JSON with placeholders the agent must fill from measurements, and blank the material column (or mark it TBD).
23. The 2D stage is fast: about 7 s of compute for views, crops and compose. Its cost is agent turns, not tools.

## Recommended fixes, ranked by time saved and demo risk

Guiding rule (per Steve): **keep the geometry agent-generated, live, class by class.** Scripting is fine only for plumbing and measurement (API vocabulary, image metrics, PDF layout), which AGENTS.md already allows. None of the fixes below pre-writes product geometry.

**A. Remove the two loops that can't converge (render stage, ~3-5 min per run, plus the visible defect)**
1. **Pad calibration decision (issue 16).** Re-derive the pad albedo and the brightness/emissive pair once, offline, so the spec'd CMF passes G:R 0.55 / luminance ≤ 160.5 at the documented exposure. Then update the ladder table in fusion-photoreal-render. Until then, tell the agent to report the pad check once and not tune.
2. **Difference-matte compositing (issue 21).** Make the empty-plate render the standard path: hide occurrences, render the plate at the same camera and settings, matte = |render − plate| > 10. It costs one plate per view (~70-120 s at q95; test whether a q50 plate matches well enough). Fixes the halo and the plan crop.
3. **Ship the projected-ROI pad measurement (issue 17)** as a small utility; retire color-threshold blob counting for acceptance.

**B. Cut fixed waits (~2-3 min per run)**
4. **create_drawing blocks Fusion for ~2 min, and every call in that window times out (~65 s each).** Skill change: after create_drawing returns, wait 120 s doing host-side work (report, manifest), then make one check. Companion MCP change (better): run create_drawing asynchronously and return a job ID, like start_render.
5. **CMF assign order (issue 12):** body first, then only faces that differ. Measured ~13x faster per body; the full pass drops from ~70 s to ~8 s and stays clear of the 300 s timeout other harnesses hit.
6. **Do host-side work while renders run.** This run composited the hero during the plan render. Also draft the report and manifest during raytraces. Never call execute_code while a render runs (it blocks).

**C. Cut agent turn latency and context (the largest share of wall clock)**
7. **One source of truth for skills (issue 1).** Delete or disable the fusion-product-design plugin skills and agents for SLAB. Reinstall the six Cowork skills from the repo. The installed slab-run is a different, older document from the repo one. Fewer, smaller skills mean faster reading, less context, and no reconciling.
8. **Bless a utilities preamble (issue 'Helper bootstrap').** `builtins` persists across execute_code calls, so the agent can register spec §1 API vocabulary once per session instead of re-pasting ~3 KB per call. Document this in slab-product-spec §1 as allowed, with geometry still composed per call.
9. **Put tested legend outlines in the spec (issue 10)** so class 12 passes first time; it was the historic repair loop.
10. **Ship slab_sheet.json as a template (issue 22)** with placeholders filled from measurements; that removes a manual edit and a correctness risk.

**D. Demo hygiene and correctness (prevents lost runs)**
11. **Hands off Fusion during the run (issue 4).** Add a per-class guard to the skill: assert `design.activeEditObject` is a Component and that every earlier occurrence still exists before building. That guard would have caught today's silent loss in one call.
12. **Fix the stale or wrong skill statements, and add one rule:** timeline-health snippet (5); add 'a deltas body_count that disagrees with the expected running total is a stop signal' (6); brightness default 1.2 (14), progress_percent 0/50/100 (19), extrude volume label (7), DEC-C3 padded arithmetic (11), '11 appearances incl. library source' (13), appearance-fork guidance (18).
13. **Pre-approve tools** (fusion360 MCP, uv/python) in whatever harness runs the demo, so no approval prompt can stall an unattended run.

**E. Optional render-time trims (~1 min)**
14. The plan final at 1400 q95 took 117 s. If the composite crops to 918x1400 anyway, test 1200 q90 for the plan. Keep two finals per view as the cap.

### Estimated run time with A-D applied (estimate, not measured)
Build ~5 min · CMF + layout ~1 min · exposure + 2 finals + 2 plates ~6 min · composite/metrics ~0.5 min · 2D ~1 min · drawing ~2.5 min · report ~1 min → **≈ 15-17 min**, with no FAIL loops. Most of the remaining gain would come from fewer agent turns (C), which is model- and harness-dependent; measure it on the next run.

## Findings from run 2

1. **Tool calls in one batch don't overlap.** `create_drawing` and the host bash step were sent together; the host step started only after `create_drawing` timed out (14:49:01). The ~65 s drawing wait can't be hidden from the agent side. Fix: the companion MCP should make `create_drawing` asynchronous (job ID plus status, like `start_render`).
2. **Whether the lightweight drawing is faster is still unknown.** The call still hit the ~65 s timeout, but the first follow-up check succeeded, where run 1 needed a second ~65 s timeout. Finish time is between 14:49:01 and 14:50:30.
3. **Cloud `saveAs` latency varies:** 0.6 s in run 1, 54 s in run 2. In a demo, save early, ideally before the audience is watching, or show it as a visible step.
4. **The preview render measures like the final render.** Pad and housing metrics from the 1442x900 q50 preview matched run 1's 1922x1200 q95 hero to 0.1 levels. For acceptance numbers, the preview is enough.
5. **The plan viewport capture shows a large diagonal shadow** because it was captured in the Render workspace. Capture it from the Design workspace (or turn off ground shadows) next time.
6. **Pad calibration is still the open FAIL:** G:R 0.663, lum 179.5, red clipped. It needs the spec owner's decision (see run 1, issue 16).
7. The skill's DEMO profile still lists a 256 px probe; this run skipped it because the preview serves as the exposure check. Skill updated to match.

# Drawing test after run 3 — root cause and fix (15:08)

**Root cause of the slow final step:** the pinned add-in's `create_drawing` (fusion360-mcp `addon/server/render_drawing.py` @ 9d76902) hard-codes `globalPreferences.isComponentSheetGenerated = True` and `sheetCreationType = AllLevelsSheetCreationType`. Fusion therefore builds the main assembly sheets **plus one sheet per component** (11 more). The `auto_dimension` / `include_parts_list` / `isometric_view` flags don't affect that, so the "lightweight" call in runs 2 and 3 removed the iso + parts-list sheet and saved nothing.

**Fix, tested on SLAB_TOP_v6 via `execute_code` + `adsk.drawing`:** main assembly only, `FirstLevelOnlySheetCreationType`, component/sub-assembly/animation/flat/folded sheets off. Sheet 1: iso + parts list. Sheet 2: orthogonal views + overall dimensions. A3 ISO, mm.

| | Before (tool, runs 1–3) | After (API direct) |
|---|---|---|
| createDrawing | timed out at ~65 s, then another ~65 s blocked call | **27 s** (15:08:27 → 15:08:54) |
| open | (inside the above) | 6 s (→ 15:09:00) |
| total | ~2:40–3:50 | **33 s** |

Notes: the API selects sheets, not individual views. Reading `app.activeProduct.productType` right after opening the drawing raises `InternalValidationError : adapter`, so log timings to a file before opening. The canvas picture-in-Design step is removed from the default flow per Steve: drawings and the parts list belong in the Drawing workspace.

**Projected DEMO run with this drawing step:** run 3's 7:18 minus ~2:15 ≈ **~5 min**, preflight to an open native drawing (the ~58 s cloud save is still in that figure).

# Drawing crash diagnosis (15:24)

Symptom (runs 4 and 5): `Exception in acadm.crx ARX Command — Unhandled Exception c0000027 (c0000027h)` when the drawing is created. The drawing doesn't display, although the file is created in the cloud with 2 sheets (the API readback reported success).

| Test | Parts list | Auto-dimension | Result |
|---|---|---|---|
| Runs 2, 3 (MCP tool) | off | off | opened (slow, 12+ sheets) |
| Runs 4, 5 (API) | on | **on** | **crash dialog, drawing not shown** |
| Test A (API, same Fusion session, not restarted) | on | **off** | **created 19 s, opened 5 s, parts list shown, no crash** |

Conclusion: automatic dimensioning (on this 289-body model, via acadm.crx) triggers the crash. Leftover engine state is ruled out because Test A ran in the same session that crashed before. Skills updated: auto-dimension OFF; the agent must ask the user to confirm the drawing displayed, because the crash dialog is modal and invisible to the MCP. Dimensions stay on the composed A3 PDF.

Updated estimate for a clean DEMO run: run 5's 4:41 minus ~10 s ≈ **4:30**, with a native drawing and parts list that actually display.
